# QC-стенд RGBH vs RGBS для RIFE (Blackwell)

Зачем: на Blackwell (RTX 50xx, sm_120) интерполяция RIFE работает в RGBS fp32 —
это защитное правило `anime_upscale.hardware` (`recommended_interp_format`
→ `"rgbs"`, `recommended_trt` → `False`), поставленное из-за класса поломок
TRT/RIFE на sm_120 (vs-mlrt #163, NVIDIA TensorRT #4721). Дешёвый кандидат
апгрейда — **native fp16 (RGBH) без TRT**: vsrife выбирает точность по формату
клипа (RGBH = fp16, RGBS = fp32 — канон апстрима), PyTorch sm_120 стабилен
с 2.7/cu128 (проект на 2.14.1/cu130), и fp16 делит пропускную способность
памяти пополам. Перед тем как флипать правило, нужен измерительный ответ:
**безопасен ли fp16 по качеству и даёт ли он ≥10% скорости**.

Стенд — `scripts/qc_precision.py`: тот же прод-вызов RIFE 4.25 (vsrife, те же
модель/параметры из `config.toml` и `stages/interpolate.py`) гоняется дважды
на каждой из трёх детерминированных синтетических фикстур 1080p:

| Фикстура | Что проверяет | Кат-ы (из генерации) |
| :-- | :-- | :-- |
| `hard_cuts` | зона scene changes (sc-passthrough + интерполяция у кат-ов) | каждые ~1 с |
| `pan_motion` | быстрый панорамный motion + тонкие линии (jaggy-line-детектор) | нет |
| `mixed` | движение + редкие кат-ы (прод-смесь) | каждые ~2 с |

Референс = RGBS fp32 (базлайн-доверие), кандидат = формат из `--format`
(по умолчанию `rgbh` — форс ЯВНО параметром скрипта, правило `hardware.py`
не трогается и не читается). Сравнение покадровое, пиксели берутся прямо
после интерполяции (без encode — это ровно те пиксели, что уйдут энкодеру).
Клип не сплитится никогда (у vsrife нет глобального frame-offset — канон).

## Что измеряется

- **Качество**: глобальный PSNR, per-frame PSNR, mean-abs-diff, worst-кадр —
  всё между прогонами. worst-таблица (топ-10) несёт расстояние каждого кадра
  до ближайшего кат-а (индексы кат-ов известны из генерации); worst-кадр в
  зоне ≤5 исходных кадров от кат-а помечается громким предупреждением
  (кадры вокруг кат-ов — зона повышенного риска fp16).
- **Целостность**: число кадров референса и кандидата должно совпасть
  бит-в-бит (потерянный/дублированный кадр = прогон недействителен).
- **Скорость**: fps обоих прогонов (тёплый проход + медиана 3 повторов),
  пиковая VRAM через `torch.cuda.max_memory_reserved`, дельта %.
  Честная оговорка: содержимое фикстуры (numpy) пересоздаётся ВНУТРИ
  замеряемого прохода — одинаковый оверхед для обеих сторон, поэтому
  **A/B-дельта fps честна, а абсолютные цифры занижены**: их нельзя
  сравнивать с якорями benchmark.py (там декод реального клипа, здесь
  синтетика дорисовывается на лету).
- Результат: RU-вердикт в консоль + `benchmarks/<gpu-slug>/qc_rgbh.json`
  (schema_version 1) — история рядом с `anchor.json` от benchmark.py.

## Пороги (константы в шапке скрипта, не подстраивать под данные)

| Вердикт | Условие |
| :-- | :-- |
| `PASS` | global PSNR ≥ **35 дБ** И worst-кадр ≥ **28 дБ** И fps-выигрыш ≥ **10%** (по худшей фикстуре) |
| `FAIL` | качество ниже порога (скорость при этом не важна) |
| `INSUFFICIENT-GAIN` | качество в пороге, но выигрыш < 10% (в т.ч. отрицательный) |
| `ERROR` | метрики содержат NaN/inf (поломанные пиксели, нулевые различия и т.п.) — прогон недостоверен, exit 1, правило НЕ переключать |

Для ориентира: литература по RIFE-классу фиксирует типичную деградацию
fp16 против fp32 порядка 0.04 дБ PSNR — порог 35 дБ между прогонами
консервативен с большим запасом; провал ниже него означает артефакты,
а не «нормальный шум fp16».

## Как запускать на 5080

```bash
# из корня репо (после uv sync; GPU обязателен — гейт громкий без него):
uv run python scripts/qc_precision.py                 # кандидат rgbh vs референс rgbs
uv run python scripts/qc_precision.py --dry-run       # план без выполнения
uv run python scripts/qc_precision.py --seconds 8 --repeats 3   # длиннее/точнее
```

Параметры: `--format {rgbh,rgbs}` (формат КАНДИДАТА), `--seconds 5..8`,
`--warmup`, `--repeats`, `--outdir`. Прогон ~5–10 минут: 3 фикстуры ×
(референс + кандидат) × (1 прогрев + 3 замера + 1 сравнение) ≈ 56 полных
интерполяций 6-секундного клипа. Модель и параметры берутся из `config.toml`
(`[stages.interpolate]`); TRT-гейт зеркалит прод (`cfg.trt AND
recommended_trt`), так что на Blackwell стенд гоняет native PyTorch —
ровно как производственный прогон.

## Что делать с результатом

1. **PASS** (все три фикстуры в пороге + выигрыш ≥10% по худшей): правило
   можно флипнуть — отдельным шагом поменять
   `HardwareProfile.recommended_interp_format` (`src/anime_upscale/hardware.py`)
   для Blackwell с `"rgbs"` на `"rgbh"`. Только после ревью владельца.
   `qc_rgbh.json` остаётся в `benchmarks/` как основание решения.
2. **FAIL**: fp16 небезопасен на этом железе/стеке — правило остаётся
   `"rgbs"`, стенд перезапускать после смены torch/TRT-версий.
3. **INSUFFICIENT-GAIN**: качество ок, но выигрыш не стоит переключения —
   правило остаётся; вернуться к идее при апгрейде драйвера/стека.
4. В любом случае смотреть worst-таблицу: если провал сосредоточен у кат-ов
   при чистом остальном потоке — это класс «интерполяция через кат-»,
   а не деградация fp16; учитывать при трактовке (sc-passthrough vsrife
   уже пропускает кат-ы без интерполяции).

Локальная валидация стенда (без GPU) — тесты `tests/test_qc_precision.py`:
детерминизм фикстур, метрики на парах с известными ответами, пороговые
кейсы вердикта, привязка worst-кадров к кат-ам, паритет прод-вызова,
JSON-схема, VS-швы на CPU. Реальный GPU-прогон — owner acceptance.
